## Intent

**Problem:** The release pipeline is built, but the Operator has no checked, written procedure to enable Actions safely under either default-branch option, to push the first Release Tag, to verify and record the release, to recover from a failed one, or to keep the mirror and the rebases safe; every one of those is a manual gate with a stated consequence if skipped.

**Approach:** Write one document, `fork/activation-runbook.md`, and nothing else: the Operator-owned procedure for the activation core (AD-8), the Run-Inventory Preflight (AD-9), the release journey, recovery, the mirror and rebase procedures (AD-13) and the readback breadth the spine defers to it, with copy-and-run read-only commands, pass and stop criteria, a sanitized evidence template, and the honest limits. Writing it authorizes nothing: each live action is a separate decision the Operator takes at that moment, and Stories 1.11 and 1.12 are where it is executed. Authoritative wording: `epics.md` Story 1.10, AD-3, AD-4, AD-7, AD-8, AD-9, AD-12, AD-13 and AD-15 of the accepted spine.

## Boundaries & Constraints

**Always:**
- `FORK.md` and the accepted spine win. The change adds only `fork/activation-runbook.md`. The evidence template is a section of that file, not a second file. No code, test, workflow, configuration, README, `FORK.md` or other file changes; nothing under `internal/`, `cmd/`, `tests/`, `scripts/` or `.github/` changes. Earlier stories' files are read-only inputs.
- **The runbook is a procedure, and authorizes nothing.** It states at its head: its owner is the Operator; it starts only after the #1 work is merged into `ezop`; it chooses neither option A nor option B; every step that changes GitHub or the repository (disabling a workflow path, adjusting a ruleset, enabling Actions, pushing a tag or a ref, re-running a run, landing a record) is taken by the Operator personally, at the time, after the preceding checks; no agent, workflow or tool performs one (AD-4); and the safe state is Actions off, which is never given up to reach safety. The decisions it needs recorded before it starts are listed: D1 (A or B); under A, an approved FR-14 path; the `FORK.md` › Following Upstream amendment approved; the FR-12 ruleset items in force and recorded in `FORK.md`; and, before the first Release Tag, the Q4 risk and the abandonment policy for `v5.1.0-ezop.1` recorded in a sanitized note under `fork/evidence/`.
- **The activation core, in this order, each step with its read-only commands, what a pass looks like and what stops it** (AD-8): (1) #1 merged into `ezop` and the `FORK.md` amendment approved, both read back; (2) with Actions off, the four Upstream paths (`release.yml`, `openapi-sync.yml`, `stats.yml`, `web.yml`) disabled by path and read back as `disabled_manually`, Q1 first, any answer other than a clear yes keeping Actions off; (3) the seven-secret readback (`AUR_KEY`, `TAP_WINGET_TOKEN`, `NPM_TOKEN`, `GPG_PRIVATE_KEY`, `GPG_PRIVATE_KEY_PASSPHRASE`, `WEB_DEPLOY_KEY`, `STATS_TOKEN`) for the repository and every environment, names only; (4) the settings readback: `default_workflow_permissions: read`, pull-request approval off, the fork-PR approval policy with its exact value recorded, Operator-only write access, the four recorded rulesets matching `FORK.md`, and the FR-12 ruleset items as an unmet prerequisite until the Operator has put them in force and read them back; (5) the option-specific state; (6) a fresh preflight; (7) enabling Actions last, outside 00:00 and 01:00 UTC; (8) the post-enable readback inside the freeze, which is Verified Activation. Any failure means Actions stay off (or are turned off at once) and D1 returns to the Operator.
- **Option-specific state.** Option A: `main` stays the default branch, and an approved FR-14 path to the Drift Guard (owner, trigger and default-branch arrangement, timing, viability proof) is required before enabling. Option B: the default branch is set to `ezop` by explicit decision with a `FORK.md` amendment, through the bracketed `main-mirror` adjustment (record the SHA of `main`; adjust `main-mirror`; change the default branch; restore `main-mirror` field by field to the `FORK.md` table; require the `main` SHA unchanged; repeat the readbacks of steps 3, 4 and 2); a failed restore keeps Actions off and is handled as an incident.
- **The Run-Inventory Preflight** (AD-9), as read-only commands with no helper code: the unfiltered run listing at `per_page` 100 paginated to the end with the enumerated count equal to `total_count`; the closed `status` and `conclusion` sets, a value outside them stopping the preflight; the runs that need a disposition (every non-completed run, every run concluded `action_required`, every completed run created or last updated in the last 30 days); the four dispositions with a named owner; the per-workflow acceptance fields and, for `fork-release.yml`, the tag-state list with each tag's `verify --status` token (an `unknown` stopping the preflight and being retried); workflow coverage as the union of the files on every origin branch and the API list; the ref and pull-request sweep (one complete `git ls-remote --refs origin 'refs/heads/*' 'refs/tags/*'` cross-checked with the API counts, `guard --profile release` on the `ezop` tip and `guard --profile mirror` on the `main` tip with the printed SHAs equal to the listed tips, every other branch accounted for, open pull requests with their head repositories, tags); the push freeze and what voids it; and the fresh readback immediately before enabling.
- **The release, recovery, mirror and rebase procedures** (FR-9, FR-12, FR-18; AD-3, AD-7, AD-13): the first Release Tag only after Verified Activation and after the Q4 risk and the abandonment policy are recorded; the Pre-Tag Gates (`just test-fast`, `just lint` leaving no diff, `just build`, `just snapshot`, in order, stopping at the first failure) on the landed commit in a clean checkout, with the gate-capture file in the six keys that `fork/verification/README.md` fixes; the base-tag peel comparison with `upstream`; `guard --pre-push TAG C` and pushing exactly its printed refspec; waiting for the run and reading `verify --status` (a run in progress reads `unknown`); `verify TAG GATES`, landing the printed record through the `FORK.md` Git workflow, and `verify --status` exit zero before Handover; the pre-re-run check (token `none` together with release None only, otherwise abandon; a full re-run only, within 30 days and at most 50 re-runs; no tag is ever deleted, moved or re-pushed) and the maintainer non-overlap procedure; abandonment (the `abandoned` record with one reason code) and the next explicitly authorized `N`, including a leftover draft, which is abandoned and never repeated (AMD-FR18-1); the compared-commit mirror fast-forward with `U` and the Actions-off steps for any `.github/` change; Upstream tag pushes after `guard --profile mirror`; the rebase checks and the `--force-with-lease` form; and the rule for a topic that changes workflow files after Verified Activation.
- **Commands are accurate and bounded.** Every helper command is the real spelling and exit meaning of the helper as it stands; the helper is built, for every Operator-side command, by the Story 1.2 recipe from a clean clone of the tip just fetched (`go build -o <outside the clone>/fork-release ./scripts/fork-release`), because the Operator-side commands refuse a binary without embedded build information, from a modified tree, or whose commit is not landed on the fetched `origin/ezop`. Every GitHub read is `gh api --method GET` with the API-version header and the repository named in the path, never `GH_REPO`; a command that writes (disable or enable a path, enable Actions, adjust a ruleset, re-run) is marked as a manual Operator write. A command whose behavior on GitHub is not established by a source the spine cites is marked unverified until its first use, and the runbook tells the Operator to stop and record any unexpected answer.
- **The readback breadth the spine defers to the runbook** is listed with a read-only command or an explicit "no command, read it in the settings" note for each: deploy keys, installed apps with write access, Pages, GitHub-managed dynamic workflows, the Dependabot secrets store and `vars`, and the GitHub-side features that create refs (web-UI branch restore and update, merge queue, Dependabot), each recorded as unused or swept.
- **The evidence template** is sanitized (counts, states, paths, versions, tag names, commit SHAs, run ids only where a disposition needs them, and times; never raw API output, account metadata, emails, local paths or secret values) and names its home, `fork/evidence/activation-<YYYYMMDDThhmmssZ>.md`, UTC to the second. The runbook tells where the other evidence goes: the post-first-release run-list and settings readback, and the per-fast-forward S4 observation with the embedded helper commit.
- **Honest limits are in the document.** The runbook lists what it cannot guarantee: Q1 to Q6 as open, the real GitHub behavior of every release step before the first run, native Windows as unsupported and untested (the Operator-side commands run the downloaded binary under a POSIX environment; use Linux or macOS), the reliance on the Operator's own `gh` login, the config-shadow residual (GoReleaser reads `.goreleaser.yaml` only if none of `.config/goreleaser.yml`, `.config/goreleaser.yaml` and `.goreleaser.yml` exists; the required `just test-fast` gate catches it in the development tree and the guard does not check it in a tagged tree; an explicit `--config` is deferred, not decided), the maintainer-procedure nature of the non-overlap rule, and that none of the documentation it cites is live proof. Nothing in it claims a risk solved that is not.
- Comments and text use US spelling and are public-safe: no secret, credential, token value, absolute path or private name.

**Never:**
- No live access of any kind during the work: no `gh` call, GitHub API call, Proton call, secret operation, Actions change, tag, release or push; every command in the runbook is written, not run. No arbitrary roles, approval ceremony, lock, queue or service. No helper code for the preflight. No `FORK.md`, README, workflow, configuration or code edit; the proposed `FORK.md` wording goes in the pull request description. The runbook does not choose between A and B and does not take D1, D2, the Q4 risk acceptance or the abandonment policy for anyone.

**Execution roles (set before dispatch; the writing child's sole source is this spec).**

**Local facts established offline before dispatch (syntax and the helper's behavior only; none of it is real GitHub behavior).**
- Build: the Story 1.2 recipe, run in a fresh clone of the repository with the pinned toolchain, produces a binary whose build information carries `vcs.revision` equal to the clone's commit and `vcs.modified=false`; the form is `go build -o <path outside the clone>/fork-release ./scripts/fork-release`, run inside the clone.
- Spellings and usage lines, as run: a bare `fork-release` prints `fork-release: no command` (exit 2); an unknown word prints `fork-release: unknown command` (exit 2); `guard` with a missing or malformed mode prints `fork-release: usage: fork-release guard --profile release|mirror COMMIT | --pre-push TAG COMMIT | --in-run | --recheck` (exit 2); `verify` with a wrong shape prints `fork-release: usage: fork-release verify --status TAG | verify TAG GATES` (exit 2); `guard --pre-push` with a tag that is not a Release Tag or a commit that is not 40 lowercase hex is usage (exit 2); `verify --status` with a tag that is not a Release Tag prints `fork-release: status: TAG is not a Release Tag` (exit 1); with a well-formed command and an `origin` whose fetch URL is not the canonical `Ezopek/proton-cli` remote, `guard --profile`, `guard --pre-push`, `verify` and `verify --status` each print `fork-release: origin: a fetch URL of origin is not the canonical Ezopek/proton-cli remote` (exit 1) before any network read. Refusals are one line `fork-release: <check>: <reason>` on standard error; nothing is printed on standard output when a command refuses.
- Output and exit codes taken from the code and its tests (not run against a provider): `guard --profile release|mirror COMMIT` prints `checked <full sha>` then `release: pass` or `mirror: pass` (or `<profile>: held, N item(s)` and one indented line per finding) and exits 0 or 1; `guard --pre-push TAG C` prints exactly `C:refs/tags/TAG` and exits 0; `verify TAG GATES` prints the record on standard output (exit 0) and nothing on a refusal; `verify --status TAG` prints `record: <token>` and `release: <state or "not read">` and exits 0 for `verified`, 3 for `none`, 4 for `unknown`, 5 for `abandoned`, 6 for `invalid`, 1 for a refusal and 2 for usage; the release states printed are `None`, `Published-Same`, `Draft`, `Other`, `Unknown`.
- The six gate-capture keys, compared by script: the `attested.*` fields of `fork/verification/README.md` and the helper's key list are the same six, `gate-commit`, `gates`, `go-version`, `goreleaser-version`, `lint-diff`, `snapshot-version`; `gates` must be exactly `test-fast,lint,build,snapshot` and `lint-diff` exactly `none`; the capture file is plain text, one `key: value` per line (one space after the colon), printable ASCII, LF, no blank line, each key once, at most 64 KiB. The record keys start `schema`, `tag`, `status`, `time`; an abandoned record adds only `reason`, one of `refused`, `failed`, `draft`, `window-passed`, `rebased`, `operator-decision`.
- `git ls-remote`, as run over a scratch repository: plain `git ls-remote origin` also lists peeled tag lines (`^{}`) and `refs/pull/*`; `git ls-remote --refs origin 'refs/heads/*' 'refs/tags/*'` lists exactly the branches and tags once each (the counts to record); asking for one tag that is not there succeeds with no output (absence), while a failed read exits non-zero (128 for an unknown remote) and is never absence.
- `gh api` (local help only; no login, no request made): `--method` (`-X`), `--header` (`-H`), `--paginate`, `--slurp` (wraps all pages into an outer array, to be used with `--paginate`), `--jq` (`-q`), `--hostname`, `--silent`, `--include`. Real pagination, `Link` header and `total_count` behavior on GitHub is unverified.

## Design Notes

- **Decisions made here, not intent gaps.** The architecture and the epic fix the content, not the form:
  - **One file, template inside.** The epic allows a second file for the evidence template; a section of the runbook is smaller and keeps the diff to one path. The Operator copies it to `fork/evidence/activation-<stamp>.md` when activating.
  - **Commands are read-only and copy-and-run, writes are marked.** Reads use `gh api --method GET` with the API-version header and the repository named in the path, in the way the helper's own adapter does, so a typo cannot become a write. The few writes the procedure needs are Operator manual steps by AD-4 and are marked as such.
  - **Retry means a re-run, never a re-tag.** The PRD's older wording allows deleting and re-pushing a tag that never reached a release; `FORK.md` makes every tag immutable even before publication and wins. The runbook's "retry" is the full re-run of the original run, only for token `none` with release None, within the platform limits; any other state is abandonment and the next `N`.
  - **The pre-re-run check is read from two lines.** `verify --status` prints `record:` and `release:`; the rule needs both (`none` and `None`), so exit code 3 alone is not enough. The helper's small pure function for that rule has no caller; the runbook states the rule in words.
  - **Supported hosts.** Linux and macOS shells with `git`, an authenticated `gh`, `jq` and the pinned toolchain through `devbox`; native Windows is not supported or tested.
  - **Unverified commands are labeled, not hidden.** Where no cited source establishes an endpoint or value (the fork-PR approval policy, deploy keys, Dependabot secrets and variables, Pages, apps, dynamic workflows), the runbook says so and tells the Operator to stop and record any unexpected answer.
- **Real journey.** After #1 is merged and the decisions are recorded, the Operator follows the core with Actions off, takes the preflight inside the freeze, enables Actions last, and keeps the activation evidence; later runs the Pre-Tag Gates on a landed commit, checks the base tag, runs `guard --pre-push`, pushes the printed refspec, waits, runs `verify`, lands the record and reads `verify --status` before any Handover; and keeps the mirror and the rebases inside the same discipline. Any failed check leaves Actions off.
- **Proposed `FORK.md` wording (for the pull request description; `FORK.md` is not edited here):**
  - *Releasing:* the full Pre-Tag Gates on every release, in a clean checkout of the landed commit; the first Release Tag only after Verified Activation; verification before Handover and one append-only terminal record per tag; `guard --pre-push` before every tag push; abandoned releases never deleted; the retry rule: a retry of a Release Tag is safe only when no GitHub release object and no verification record exists for it, and it is a full re-run of the original run after `verify --status` shows token `none` with release None; if any draft or public release object exists, the Operator records abandonment and the repair uses the next explicitly authorized `N`.
  - *Following Upstream:* Upstream release tags are pushed one at a time after `guard --profile mirror` on the peeled commit; the `.github/` comparison against the recorded commit `U`, with not applying as the default; no rebase while a release is open, the `--force-with-lease` form naming the checked SHA, and the old-to-new SHA mapping; the activation ref sweep and the rule that a topic changing workflow files takes Actions off first; the final rulesets that meet the FR-12 items, recorded in the ruleset table by the Operator; and the manual gate ledger as the statement of each gate's owner and recovery.
- **Size.** About 6,000 tokens by a chars/4 estimate (3,687 words, 24,100 bytes), above the 900 to 1,600 guide, and the document it specifies will be several times longer. One story is recommended: the core, the preflight and the release journey reference each other. One implementation turn is expected, in three passes over the same file.
