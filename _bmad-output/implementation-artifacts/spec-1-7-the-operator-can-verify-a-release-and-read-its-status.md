## Intent

**Problem:** Nothing yet observes a published Fork Release as a whole and turns it into a Verification Record, and nothing tells the Operator, or the later Handover consumer, in one token whether a tag's record, release and run agree.

**Approach:** Add, in `scripts/fork-release/`, two Operator-side commands. `verify TAG GATES` makes every observation of a published release (the tag's commit, the notes' `Commit:` and `Run:` lines, the downloaded assets against `checksums.txt` in both directions, the host binary's version, the named workflow attempt, and the last two re-reads), then prints the record and writes nothing. `verify --status TAG` makes four reads and prints `record: <token>` and `release: <state>` by the accepted nine-row status table, exiting zero only for `verified`. Authoritative wording: `epics.md` Story 1.7 and AD-7 of the accepted spine.

## Boundaries & Constraints

**Always:**
- `FORK.md` and the accepted spine win. Outside `_bmad-output/`, the change touches only files under `scripts/fork-release/`; no `go.mod` or `go.sum` change, nothing under `internal/`, `cmd/`, `tests/`, `fork/` or `.github/`, and `.goreleaser.yaml`, `justfile`, `devbox.lock` and `README.md` stay byte-identical. Earlier stories' behavior and assertions are kept; edits to old files are only those listed in the Code Map. The accepted status table is not rewritten.
- **Wire.** Exactly `verify --status TAG` and `verify TAG GATES`; anything else, including a bare `verify`, `verify --status` without a tag, or extra arguments, is one usage line, exit 2, with no read of anything. A `TAG` that is not a Release Tag is a refusal before any network read. Refusals are one line `fork-release: <check>: <reason>` (checks `verify` and `status`, and the existing names for identity), exit 1; reasons come from a closed set and never quote a response, a URL, a file or the binary's output. A command that refuses prints nothing on standard output.
- **Helper identity (both commands, the Story 1.2 checks, unchanged in behavior).** Every fetch and push URL of `origin` is canonical; the binary has `vcs.revision` and `vcs.modified=false`; one fetch of `ezop` is taken at the start and the helper's own commit equals that tip or is its ancestor (`git merge-base --is-ancestor`, only exit status 0 passes; any other status or a failed fetch refuses). The existing inline sequence of `guard --profile` becomes one shared function used by all three; its order and its tests are kept.
- **Reads.** Only `gh api --method GET` with the API-version header and the constant owner and repository, through the pinned adapter, each new path shape allowed by the validated pattern and its argv pinned by a test. New shapes: the workflow of `fork-release.yml` by file name; the runs of that workflow filtered by `event=push` and `head_sha`, 100 a page, pages by number; a run by id; a run attempt by id and number. Digits are bounded; any other path is refused before `gh` runs. The tag is read once from origin with `git ls-remote` through the existing `OriginTags`, peeled to `E`; success without the tag is absence, a failed read is a failure. The record and release reads are the existing lookups. The release lookup answer is extended to carry the `Run:` line of a Published-Same release (the raw value and whether exactly one valid line was found), without changing any existing classification.
- **`verify TAG GATES`** performs, and makes ALL of these before it prints anything (a failed read of any kind prints nothing and refuses; a transient failure is simply retried by the Operator):
  1. Reads `GATES`: a regular file of at most 64 KiB, plain text under the record's own line rules, with exactly the six capture names (the `attested.*` fields of the record without their prefix, taken from the helper's key list, no second list), each once. Its values are judged by the record validator when the record is composed, and `gate-commit` must equal `E`.
  2. Takes `E` from the peel of `TAG` in its own read; requires the record lookup to be Absent and the release lookup to be Published-Same for `E` (so the `Commit:` line equals `E`); requires `E` to be an ancestor of the fetched `origin/ezop` tip (status 0 only).
  3. Reads the tool identity from the tree of `E` (never the working tree), as AD-7 lists it: the Go version of `go.mod`; the Go and GoReleaser versions of `devbox.lock`; the workflow's GoReleaser pin, the one top-level `env` entry `GORELEASER_PIN` of `.github/workflows/fork-release.yml` (the name the in-run guard already reads), a plain `vX.Y.Z` string in a file that parses without duplicate keys or merges; and the git blob ids of `.goreleaser.yaml` and `devbox.lock`. The existing toolchain check must pass with that pin (exactly one `goreleaser@` and one `go@` lock package, equal to the pin and to the `go.mod` version), so `go-version` and `goreleaser-version` are the values it vouches for. A missing, unreadable, malformed, repeated or different pin, or any other missing or inconsistent file, refuses.
  4. Requires every asset of the release to be `uploaded`; downloads every one from the published release through the pinned download seam (never `dist/`); parses `checksums.txt` with the shared strict parser; requires every listed name to be a downloaded asset whose sha256 equals the listed hash, and the six binary names (`selfmanage.AssetName`, no second list) to be listed. Every downloaded asset other than `checksums.txt` that is not listed is named in `exceptions`.
  5. Runs the host binary (`selfmanage.AssetName(runtime.GOOS, runtime.GOARCH)` must be one of the assets) with `version -o json` through the existing bounded runner and requires the JSON `version` to equal `TAG` without its leading `v`.
  6. Reads the one `Run: <run_id>/<run_attempt>` line (a missing, repeated or malformed line refuses), reads that attempt and requires `status` completed, `conclusion` `success`, `head_sha` equal to `E`, `event` `push` and `workflow_id` equal to the id of `fork-release.yml` read by file name; reads the run and requires its `run_attempt` to be at least the named attempt.
  7. As its last two reads: the release again, still Published-Same with the same `Run:` line; then the runs of `fork-release.yml` with event `push` and head SHA `E`, fully paginated and count-reconciled (a failed or short page, a count that does not reconcile, or more than the documented search cap is a refusal), with no run that is not `completed`.
- **The printed record** is the one record of the Story 1.4 grammar, in its field order: header (`schema` 1, `tag`, `status` verified, `time` the current UTC second), `commit`, one `asset.<name>` line per downloaded asset (`checksums.txt` included), sorted bytewise, `exceptions`, `host-platform` (`GOOS/GOARCH` of the host), `proton-version`, the two blobs, `go-version`, `goreleaser-version`, `run-id`, `run-attempt`, `run-conclusion` (`success`) and the six `attested.*` values. Before printing, the command parses its own output with the Story 1.4 record parser and refuses on any finding, so a record that would fail the landing validator is never printed. It writes no file; the only thing it creates is a private temporary directory for the host binary, removed before it returns. No record text is printed by `verify --status`.
- **`verify --status TAG`** reads, in this order: the record lookup; then, only when the record is Absent or a valid verified record, the release lookup, the read of `TAG` from origin and the run listing for `E` (`E` is the peel for an Absent record and the record's own `commit` for a verified one; an absent or failed peel gives the release lookup the all-zero SHA, so a published release reads Other and never Same, and without a peel no listing is made: an absent tag is row 4 and a failed read is row 3 or 7). It downloads and rereads no asset. It prints `record: <token>` and `release: <state>` (`not read` when the record alone decided: rows 1, 2, 5 and 6), the token by the first matching row of the status table below, and exits 0 only for `verified`; `none` 3, `unknown` 4, `abandoned` 5, `invalid` 6. A record is judged valid by the Story 1.4 parser for the lookup's tag (a malformed, partial or other-tag file is row 5; a directory or submodule at the path is row 2). A run is non-terminal unless its `status` is `completed`; an unknown status value counts as non-terminal.
- **Pre-re-run rule.** One small pure function holds the Operator's rule "a re-run needs token `none` together with release None" and a test shows it refuses the record-Absent, release-Unknown fixture; no command calls it and no new behavior hangs on it.
- Tests use fakes, scratch repositories and a stand-in program only (the existing helpers); no `gh` run, no download, no network, no real tag, release, repository, run or credential, no skip. Comments and docs use US spelling and are public-safe. Gates run through the pinned toolchain with the recipes under Verification; never `just test` or any `go test` pattern that reaches `tests/live`.

**Never:**
- No record file written or edited, no landing, no confirmation step, no retry loop, lock, queue, service or state file, no new dependency, no write call to GitHub, no change to a file under `internal/` or to `fork/`, `FORK.md`, README, a workflow or the release configuration, no Actions, tag, release or settings change.
- No `--pre-push` (Story 1.8), no workflow or caller (Story 1.9), no runbook text (Story 1.10). No reread of asset bytes by `verify --status` (the Handover consumer's byte check is deferred by the architecture). No skipped, weakened or disabled test or gate.

### Implementation record

Two native implementation turns wrote the code in four test-first slices: the reads and the `Run:` line on the release answer; the shared helper-identity function and `verify --status`; the pure pieces of `verify` (capture, two-way checksums, tool identity with the workflow pin, record render); and `verify TAG GATES` with its dispatch. Each slice has a compile failure on the missing names (or a direct assertion failure where the API existed), a runnable assertion failure, and a green run; the logs are kept with the story's private evidence. The identity extraction was a refactor: the old guard tests were green before, and green again after it.

Choices inside the frozen intent: for an Absent record the tag is read first, then the release and the listing, because the release lookup needs the peel as its commit; a verified record uses the same order. A word that starts with a dash is treated as an option, so `verify --confirm X` and `verify TAG --status` stay usage (a gates path starting with a dash is written `./-x`). The gate capture is refused when it is a symlink. `verify` keeps only the sha256 of each asset, plus the bytes of `checksums.txt` and of the host binary. The workflow pin is read by one small function in `verify.go`; it refuses any merge key as well as duplicate keys. ## Design Notes

- **Decisions made here, not intent gaps.** The architecture fixes the observations and the table, not the wire or some record details:
  - **Exit codes** `none` 3, `unknown` 4, `abandoned` 5, `invalid` 6; the printed `record:` token is the stable interface for the Handover consumer, the number is for scripts, and 1 and 2 stay the refusal and usage codes.
  - **Reads are lazy by record.** A record that decides alone (rows 1, 2, 5, 6) makes no further read, so a failed read cannot strand an abandoned tag; the release line then says `not read`. For an Absent record the release is read against the peel of the tag, or against the all-zero SHA when there is none (a published release can then only read Other).
  - **Terminal means `completed`.** The docs mix statuses and conclusions in one vocabulary; the helper treats anything but `completed` as non-terminal, which fails closed and may need loosening after the first real observation (Q6).
  - **Tool identity** follows AD-7 exactly: `go.mod`, `devbox.lock`, the workflow's pin and the `.goreleaser.yaml` blob at `E`. The pin is the top-level `env.GORELEASER_PIN` of `fork-release.yml`, the name Story 1.5 already gave the in-run guard; Story 1.9's workflow must declare it there, and its `release` profile will pin that side. `verify` cannot pass on a tree without the workflow, which is right: a Fork Release has one. Tests give a scratch tree a minimal workflow, so no live workflow is needed. (A first draft left the pin out because the workflow does not exist yet; that contradicted AD-7 and was corrected before adoption, as a source alignment and not a new decision.)
  - **`checksums.txt` is an asset line** of the record (it was downloaded and the consumer can check it) and never an exception. Capture file: the six names in any order, each once.
  - **Verify validates its own output** with the record parser before printing, so a hand-edited name or value cannot yield a record the landing validator rejects. The pre-re-run function exists because the acceptance asks a test to show the rule refusing; it has no caller.
  - The tag is read with `OriginTags` (`git ls-remote`, no local ref), one call per command; objects for the ancestry test come from the single `ezop` fetch.
- **Real journey.** After the `stamp` job is green, the Operator builds the landed helper, runs the gates while capturing their facts, runs `verify v5.1.0-ezop.1 gates.txt`, lands the printed record as `fork/verification/<tag>.md` through the pull request workflow, and before any Handover or re-run reads `verify --status <tag>`. A read that fails is retried; a refusal for the release itself ends in an `abandoned` record and the next `N`.
- **Size.** The spec is well above the 1,600-token guide. The commands share the lookups and the identity function, so one story is recommended; the four tasks are ordered so that clusters 1 and 2 (the reads and `verify --status`) can be a first implementation turn and clusters 3 and 4 (`verify`) a second, under this one spec.
