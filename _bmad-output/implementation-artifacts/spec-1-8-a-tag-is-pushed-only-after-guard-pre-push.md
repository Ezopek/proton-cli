## Intent

**Problem:** A Release Tag is immutable once pushed, yet nothing checks, before the push, that the commit it will name is landed, that the tag does not exist, and that every offline check of the release run already accepts that commit; and a push that names the tag only by a local ref could bind the tag to a different commit than the one checked.

**Approach:** Add, in `scripts/fork-release/`, `guard --pre-push TAG C`: it runs the offline checks against the tree of the candidate commit `C`, with fresh reads of `origin`, and only then prints exactly `C:refs/tags/TAG`, so the tag pushed is bound by value to the checked commit. It pushes nothing, reads no local tag and no Actions state. Authoritative wording: `epics.md` Story 1.8 and AD-3 (pre-push identity) of the accepted spine.

## Boundaries & Constraints

**Always:**
- `FORK.md` and the accepted spine win. Outside `_bmad-output/`, the change touches only files under `scripts/fork-release/`; no `go.mod` or `go.sum` change, nothing under `internal/`, `cmd/`, `tests/`, `fork/` or `.github/`, and `.goreleaser.yaml`, `justfile`, `devbox.lock`, `README.md` and `FORK.md` stay byte-identical. Earlier stories' behavior and assertions are kept; the one old test row that pins `--pre-push` as unknown (a placeholder named "pre-push still unknown") is replaced by the new behavior and nothing else of an old test changes.
- **Wire.** Exactly `guard --pre-push TAG C`. `TAG` must match the Release Tag pattern and `C` must be 40 lowercase hex characters; any other shape, a missing argument or an extra argument is the one guard usage line, exit 2, with no read of anything (the usage line names the new mode). Every refusal below is one line `fork-release: <check>: <reason>`, exit 1, reasons from a closed set that never quote a URL, a response or a file; a refusing command prints nothing on standard output. Success prints exactly one line, `C:refs/tags/TAG` with `C` written out as the 40-hex commit, and exits 0.
- **The checks**, every failed read being a refusal, in this order, so that no network read is made when a local check already fails:
  1. `origin` is `Ezopek/proton-cli` on every effective fetch and every push URL (the existing check, unchanged).
  2. The helper's embedded commit equals `C` and its build is clean (`vcs.revision`, `vcs.modified=false`; the existing build-identity check supplies the revision). Missing build information, a modified tree or any other commit is a refusal. This ties the code that gates the push to the code that will run at `C`. Landedness of the helper is not a separate check: it follows from the next one.
  3. One fresh fetch of `ezop` succeeds, `C` resolves to itself as a commit (an annotated-tag object id or any non-commit is refused), and `C` is the fetched tip or one of its ancestors (`git merge-base --is-ancestor`, only status 0 passes; status 1 and any other status refuse differently). A commit that is not on `origin/ezop`, such as a pull request head from before a rebase and merge, fails here.
  4. One fresh listing of the tags of `origin` (the existing `git ls-remote`, which writes no local ref) succeeds and does not hold `TAG`. This is positive absence: a tag already there is a refusal even at `C`, and a failed or malformed listing is a refusal, never absence. The same listing feeds the next check.
  5. A fresh fetch of the Upstream release tags succeeds: the listed tags whose names match the Upstream tag pattern (`vX.Y.Z`, the base candidates) are fetched from `origin` by name, each with an explicit `refs/tags/<name>` refspec and no destination, so that their objects are present for the ancestry test and only `FETCH_HEAD` changes; no local ref or tag is created or updated. With no such tag nothing is fetched (the base check then refuses). A failed fetch is a refusal.
  6. The Upstream Base of `C` (the existing base function over that listing) exists and equals the tag's `X.Y.Z`.
  7. The `release` profile holds nothing against the tree of `C` (the existing profile function; every finding becomes a refusal line), and the toolchain check passes on the tree of `C` with the GoReleaser pin read from that tree: the top-level `env.GORELEASER_PIN` of `.github/workflows/fork-release.yml`, read by the pin reader of Story 1.7, then the existing toolchain check against `go.mod` and `devbox.lock`. A missing, unreadable, malformed or different pin refuses. Every tree read is of the tree of `C`, never the working tree.
  8. The record and release lookups (the existing ones, with the Operator's own credential) give record Absent and release None for `TAG` and `C`: the existing refusal decision, so every other pair, Unknown included, refuses.
- **Purity.** The command makes only reads: no push, fetch into a local ref, tag, ref, index or configuration write; it reads no local tag and no local branch; it reads no Actions state and no activation record (no `actions/...` endpoint is asked for); it makes no write call to GitHub. `--pre-push` neither enables nor assumes Actions: the order "first tag only after Verified Activation" is the Operator's step. The printed refspec is for a plain `git push origin <refspec>`; `--tags`, `--follow-tags` and a leading `+` are never part of it.
- Reads of GitHub use the existing pinned adapter and lookups; no new endpoint shape is added. Git uses the existing adapter methods plus one new thin one, the tag fetch of check 5, offered as an optional capability of the real adapter (so the existing fakes and the `gitRepo` interface are unchanged); its argv is pinned by a test, its names are only those matching the Upstream tag pattern, and a git without the capability is a refusal.
- Tests use fakes, scratch repositories and a stand-in program only (the existing helpers); no `gh` run, no network, no real tag, release or repository of this checkout, no skip. Comments and docs use US spelling and are public-safe. Gates run through the pinned toolchain with the recipes under Verification; never `just test` or any `go test` pattern that reaches `tests/live`.

**Never:**
- No tag or branch is created or pushed by the helper, no `git push`, no local tag read, no Actions or activation read, no lock, queue, service or state file, no new dependency, no write call to GitHub.
- No workflow (Story 1.9), no runbook text (Story 1.10), no `FORK.md`, README or `fork/` edit: the proposed `FORK.md` wording is carried in the pull request description. No skipped, weakened or disabled test or gate.

## Design Notes

- **Decisions made here, not intent gaps.** The architecture fixes what `--pre-push` must establish, not the wire or the order:
  - **Order is cheap and local first**: shape, origin URLs, the embedded commit, then the fetch of `ezop`, the tag listing, the fetch of the Upstream tags, the base, the profile and toolchain on the tree of `C`, and last the two GitHub lookups. AD-3 lists the predicates without an order; this order makes no network read when a local fact already fails, and matches `helperIdentity`'s order.
  - **A shape error is usage (exit 2), not a refusal.** It is judged from the command line alone, and the two old rows (`--pre-push T C` and `--pre-push v5.1.0-ezop.1 abc`) already pin it as usage.
  - **The tag read is one `ls-remote` listing**, the same one the base check needs, so absence and base candidates come from one snapshot, followed by a real fetch of the Upstream tags by name (check 5). AD-3 says "a fresh fetch of origin, for the ezop branch and for tags (the AD-11 base check reads origin tags)"; a first draft listed the tags without fetching their objects and let the base check refuse when an object was missing, which did not meet that sentence. It was corrected before adoption as a source alignment, not a new decision. The accepted architecture forbids remote writes and trusting local tags; it does not forbid fetching, and this fetch writes only `FETCH_HEAD`, like `FetchEzop`. An isolated temporary repository or a private ref namespace was not needed.
  - **The pin comes from the tree of `C`**, through the Story 1.7 reader, because `--pre-push` has no workflow environment. This makes `fork-release.yml` with a top-level `env.GORELEASER_PIN` a precondition at `C`, which Story 1.9 provides. Before it exists, `--pre-push` correctly refuses real candidates; tests give a scratch tree a minimal workflow.
  - **The helper is built at `C`.** Embedded commit equals `C` means the Operator builds the helper from a clean clone checked out at the commit to be tagged, with the documented recipe; a stale helper is refused.
- **Real journey.** The Operator lands the candidate on `ezop` through the pull request workflow, runs the Pre-Tag Gates on that exact commit, checks it out in a clean clone, builds the helper there, runs `fork-release guard --pre-push <tag> <commit>`, and pushes only the printed refspec with `git push origin <refspec>`. Any refusal is fixed by a forward change or by choosing the next `N`; a tag is never re-pushed.
- **Proposed `FORK.md` › Releasing wording (for the pull request description; `FORK.md` is not edited here):** "Before every push of a Release Tag, run `fork-release guard --pre-push <tag> <commit>` with a helper built from a clean clone checked out at that commit, and push only the exact refspec it prints, `git push origin <commit>:refs/tags/<tag>`. Never push a tag by name from a local ref, and never use `--tags`, `--follow-tags` or a leading `+`. A refusal means no tag is pushed."
- **Size.** About 4,400 tokens by a chars/4 estimate (2,799 words), above the 900 to 1,600 guide; one story is recommended (the shape rule, the command and the end-to-end run only make sense together). The guide is not a gate.
