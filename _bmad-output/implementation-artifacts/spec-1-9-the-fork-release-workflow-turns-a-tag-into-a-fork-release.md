## Intent

**Problem:** The helper commands that guard, annotate, publish-check and stamp a release exist, but nothing calls them in order on a tag push, and the `release` profile neither pins the shape of such a workflow nor is run over the real repository tree, so a workflow edit could silently drop a guard.

**Approach:** Add `.github/workflows/fork-release.yml`, the only workflow that publishes (tag push only, two jobs, the guards first, GoReleaser at the pinned version, then the asset and stamp checks); extend the `release` profile so it pins that workflow's own shape, with scratch-fixture tests for each predicate; and add the actual-tree test that runs the profile over the real tree. Landing this is not activation: Actions stay disabled and no run, tag or release happens. Authoritative wording: `epics.md` Story 1.9, AD-4, AD-5, AD-6, AD-10 and AD-13 of the accepted spine.

## Design Notes

- **Decisions made here, not intent gaps.** The architecture and the epic fix the workflow's guarantees and order, not every detail:
  - **The helper is built in each job from the checked-out tree** (`go build` into `$RUNNER_TEMP`), because the in-run commands must be the code at `E` (AD-7) and the workflow has no other way to obtain it. The `stamp` job builds it too, since it runs in a separate runner; it needs no full history.
  - **The stamp is a separate read-only job**, as AD-4 and AD-6 say; the epic's phrase "stamp runs the stamping check" in the release step list is read that way.
  - **`--clean` is used** with `release`; on a fresh runner it changes nothing and it removes a stale `dist/`. It is confirmed with the source (AQ-2) before it is pinned.
  - **The shape is pinned as data in the helper** (the expected steps, with exact `run` bodies and `with`/`env` maps), not as a copy of the whole file, and the tests derive their healthy fixture from the real file. A step key outside `name`, `uses`, `run`, `with`, `env` is held because `if`, `continue-on-error` or `shell` could turn off a guard.
  - **The pin lives in the top-level `env`**, where the in-run guard, `--pre-push` and `verify` already read `GORELEASER_PIN`; the GoReleaser step references it, so the version is declared once.
  - **The shape check sits in `CheckRelease`, not in `checkWorkflows`**, so the Story 1.1 shared-rule tests keep their skeleton; the three `CheckRelease` tests and the pre-push fixture are fitted to the conforming workflow.
  - **A tree without the workflow still passes the profile** (the earlier stories' trees do); presence is required by the actual-tree test only.
  - **The real-tree toolchain consistency** (pin, `go.mod`, `devbox.lock`) is included because a mismatch would make the first guard refuse and spend a version; it is read-only and uses the existing functions.
- **Real journey.** The Operator lands this topic with Actions off; after Story 1.10's runbook and Story 1.11's activation, tags a landed commit after `guard --pre-push`; the workflow runs the guards, writes the notes, re-reads the record and release, publishes with GoReleaser, checks the assets, and the read-only job runs the uploaded binary; the Operator then runs `verify TAG GATES`, lands the record and reads `verify --status` before any Handover. A red run after publication spends the version.
- **Proposed `FORK.md` › Conventions wording (for the pull request description; `FORK.md` is not edited here):** "Workflows that belong to the fork use a `fork-` file name and never take an Upstream workflow path. `fork-release.yml` is the only workflow that publishes; its shape is pinned by the `release` profile of `scripts/fork-release`, and a change to it is a reviewed topic that changes the pin in the same commit and lands with Actions off."
- **Size.** About 5,000 tokens by a chars/4 estimate (2,926 words, 19,979 bytes), above the 900 to 1,600 guide. One story is recommended: the workflow, its pin and the real-tree test only make sense together. Two implementation turns are natural (the workflow, its shape pin and the fixture fits; then the actual-tree test), under this one spec.
